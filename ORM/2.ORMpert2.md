# 9. Installation

## Why installation is needed

Python does not include SQLAlchemy by default.

You must install it into your project's virtual environment.

---

## Why use a Virtual Environment?

Imagine two projects:

Project A:

```text
SQLAlchemy 2.0.40
```

Project B:

```text
SQLAlchemy 2.1 (future)
```

If both share the same global Python installation, version conflicts can occur.

A virtual environment isolates dependencies.

```text
Project A
│
└── .venv
     └── SQLAlchemy 2.0

Project B
│
└── .venv
     └── Different versions
```

---

## Create Virtual Environment

Windows

```bash
python -m venv .venv
```

Activate

```bash
.venv\Scripts\activate
```

Linux/macOS

```bash
python3 -m venv .venv
source .venv/bin/activate
```

---

## Install SQLAlchemy 2.x

```bash
pip install "sqlalchemy>=2.0,<3.0"
```

---

## SQLite

No extra driver installation is required because the Python standard library already includes the `sqlite3` module.

---

## PostgreSQL Driver

```bash
pip install psycopg[binary]
```

---

## MySQL Driver

Common choices include:

```bash
pip install pymysql
```

or

```bash
pip install mysqlclient
```

---

## Verify Installation

```bash
pip show sqlalchemy
```

# 10. Code

At this stage, we'll build the smallest possible ORM example.

> Some classes (`DeclarativeBase`, `Mapped`, `mapped_column`, etc.) will be explained deeply in later lessons. For now, focus on the overall picture.

```python
# Import SQLAlchemy engine creation function
from sqlalchemy import create_engine

# Import the modern SQLAlchemy ORM base class
from sqlalchemy.orm import DeclarativeBase

# -----------------------------------------
# Database URL
# -----------------------------------------
# sqlite:/// means:
# Use a SQLite database file named student.db
DATABASE_URL = "sqlite:///student.db"

# -----------------------------------------
# Create the Engine
# -----------------------------------------
# The Engine knows how to communicate
# with the database.
engine = create_engine(DATABASE_URL)


# -----------------------------------------
# Base class
# -----------------------------------------
# All ORM models will inherit from this class.
class Base(DeclarativeBase):
    pass
```

---

## Explain Every Line

### Import create_engine

```python
from sqlalchemy import create_engine
```

This imports the function responsible for creating the connection interface to the database.

Think of it as building a road between Python and the database.

---

### DATABASE_URL

```python
DATABASE_URL = "sqlite:///student.db"
```

This tells SQLAlchemy:

> Use SQLite.

> Store data in `student.db`.

---

### Engine

```python
engine = create_engine(DATABASE_URL)
```

The engine **does not immediately open a permanent database connection**.

Instead, it creates an object that knows:

* how to connect,
* how to issue SQL,
* and how to obtain connections when needed.

---

### Base Class

```python
class Base(DeclarativeBase):
    pass
```

Every ORM model will inherit from `Base`.

Later:

```python
class Student(Base):
    ...
```

This inheritance tells SQLAlchemy:

> "Student is a database table."

---

# Old Syntax vs New Syntax

Old SQLAlchemy 1.x

```python
Base = declarative_base()
```

Modern SQLAlchemy 2.x

```python
class Base(DeclarativeBase):
    pass
```

Always use the newer approach in new projects.

# 13. Advantages of ORM

## 1. Less SQL to Write

Instead of manually writing many SQL statements, you mostly work with Python objects.

---

## 2. Easier Maintenance

Changing a model often requires changes in fewer places than updating many raw SQL queries.

---

## 3. Object-Oriented Design

Your application remains consistent with Python's class-based programming style.

---

## 4. Safer Queries

ORMs use parameterized SQL by default, which greatly reduces SQL injection risks.

---

## 5. Database Portability

Moving from SQLite to PostgreSQL often requires fewer code changes than rewriting raw SQL, though some database-specific differences may still need attention.

---

## 6. Faster Development

Developers spend more time building business logic and less time writing repetitive SQL.

---

# 14. Disadvantages

## Performance

ORM adds a small amount of overhead compared with carefully optimized raw SQL.

---

## Learning Curve

There are many concepts to learn:

* Engine
* Session
* Models
* Relationships
* Transactions
* Migrations

---

## Hidden SQL

Sometimes developers forget what SQL is actually being executed.

Understanding SQL remains essential.

---

## Complex Queries

Very advanced reports or analytics may be easier to write directly in SQL.

---

## Memory Usage

Loading many ORM objects at once consumes more memory than streaming raw rows.

---

# 15. Best Practices

Senior developers typically follow these guidelines:

* Keep models in a dedicated `models.py` or `models/` package.
* Separate CRUD logic from application logic.
* Use one session per request in web applications.
* Close sessions properly.
* Use type annotations.
* Prefer SQLAlchemy 2.x APIs.
* Understand the generated SQL.
* Keep model classes focused on data representation.

---

# 16. Common Beginner Mistakes

### Mistake 1

Thinking ORM eliminates the need to learn SQL.

❌ Wrong.

A good backend developer should understand both ORM and SQL.

---

### Mistake 2

Putting all code into one file.

Better:

```text

models.py

crud.py

main.py
```

---

### Mistake 3

Ignoring generated SQL.

Always understand what SQLAlchemy is sending to the database.

---

### Mistake 4

Using outdated tutorials based on SQLAlchemy 1.x syntax.

Prefer the modern 2.x documentation and examples.

# 17. Interview Questions

## Beginner

**Q1. What is ORM?**

Expected Answer:

ORM maps database tables to Python classes and database rows to Python objects.

---

**Q2. Why use SQLAlchemy?**

Expected Answer:

It simplifies database programming while still allowing access to SQL when needed.

---

## Intermediate

**Q3. Can ORM replace SQL completely?**

Expected Answer:

No. SQL knowledge is still important for debugging, optimization, and advanced queries.

---

## Advanced

**Q4. What are the trade-offs between ORM and raw SQL?**

Expected Answer:

ORM improves productivity and maintainability, while raw SQL may offer more direct control and, in some cases, better performance.

---

## HR

**Q5. Why did you choose SQLAlchemy?**

Expected Answer:

Because it is a mature, flexible Python ORM that supports modern development practices and multiple databases.

---

## Scenario

Your application becomes slow.

Would you replace everything with raw SQL?

Expected Answer:

Not necessarily. First measure performance, inspect the generated SQL, optimize queries, add indexes where appropriate, and only use raw SQL where it provides a clear benefit.

---

# 24. Quiz Answers

1. **Object Relational Mapping** — It maps Python objects to relational database tables.

2. **A Python class** — Each ORM model class typically represents one database table.

3. **A Python object (instance)** — Each instance usually corresponds to one row in the table.

4. **To improve productivity and maintainability** — Developers write Python code instead of repetitive SQL for common operations.

5. **Yes** — SQL is still essential for debugging, optimization, and advanced queries.

6. **No** — SQLAlchemy generates SQL, but developers should still understand the SQL being executed.

7. **It acts as the bridge between Python code and the database**, translating ORM operations into SQL.

8. **To isolate project dependencies** — Different projects can use different package versions without conflicts.

9. **Many relational databases**, including SQLite, PostgreSQL, MySQL, Oracle, and SQL Server.

10. **Because it uses the current, supported API**, with better typing, clearer patterns, and long-term compatibility.

# 26. Professional Tips

These are habits followed by experienced Python/FastAPI backend developers:

1. **Learn SQL first, then master the ORM.** An ORM complements SQL—it doesn't replace it.

2. **Always inspect generated SQL** when debugging performance or correctness.

3. **Keep models focused on data**, not business logic.

4. **Use modern SQLAlchemy 2.x syntax** in all new projects. Avoid copying outdated 1.x examples.

5. **Design a clean project structure** from the beginning (`database.py`, `models.py`, `crud.py`, etc.).

6. **Treat the database as a shared resource.** Open sessions only when needed and close them properly (we'll cover this in the Sessions topic).

7. **Write type-annotated code**. It improves readability, IDE support, and long-term maintainability.

8. **Don't hide from SQL.** When an application grows, understanding joins, indexes, execution plans, and transactions becomes just as important as understanding the ORM.
