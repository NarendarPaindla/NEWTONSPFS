# 1. Simple Meaning

Imagine you have a school.

There is:

* A student
* A classroom
* A teacher
* A report card

These are all **real-world objects**.

In SQLAlchemy ORM, we also create **Python objects** that represent real things in our application.

Instead of thinking:

> "Table", "Row", "Column"

we begin thinking:

> "Class", "Object", "Attribute"

That change in thinking is the biggest ORM concept.

---

# 2. Definition

## Technical Definition

ORM Concepts are the fundamental principles that define how an Object-Relational Mapper represents relational database structures as object-oriented Python code.

These concepts include mapping:

* Classes ↔ Tables
* Objects ↔ Rows
* Attributes ↔ Columns
* Relationships ↔ Foreign Keys
* Object State ↔ Database State

---

## Simple English Definition

ORM lets us treat database data as if it were normal Python objects.

Instead of working directly with database tables and rows, we work with Python classes and objects.

# Concept 1 — Class ↔ Table

## What is a Class?

You already know Python classes.

Example:

```python
class Student:
    pass
```

A class is a blueprint.

It describes what a student looks like.

It is **not** an actual student.

---

### Real World Example

Imagine a passport application form.

The blank form is like a class.

```text
Passport Form

Name: ______

Age: ______

Country: ______
```

This form describes every passport.

But it isn't anyone's passport yet.

Similarly,

```python
class Student:
    pass
```

describes every future student.

---

### Database Side

The equivalent of a Python class is a table.

```text
Students Table

ID

Name

Age
```

Notice something interesting.

Python:

```python
class Student:
    pass
```

Database:

```text
Students
```

These two represent the same idea.

One exists in Python.

The other exists in the database.

ORM connects them.

# Concept 4 — Mapping

This is the most important ORM concept.

Mapping simply means:

> Connecting Python things with database things.

Mapping table:

| Python    | Database |
| --------- | -------- |
| Class     | Table    |
| Object    | Row      |
| Attribute | Column   |

That is why it is called

Object Relational Mapping.

# 5. Where Is It Used in Real Companies?

Nearly every modern backend system uses these concepts, regardless of the specific ORM.

For example:

* Amazon models customers, products, orders, and shipments as objects that map to database tables.
* Netflix represents users, profiles, subscriptions, and watch history as objects.
* Uber models drivers, riders, trips, and payments as domain objects.
* Google and Microsoft use similar object-oriented data models in many internal systems.

For example, an e-commerce application might have:

```text
Customer
    │
    ├── name
    ├── email
    └── phone

Order
    │
    ├── order_number
    ├── total
    └── status

Product
    │
    ├── title
    ├── price
    └── stock
```

Each of these is represented as a Python class and mapped to a database table by the ORM.

# Concept 5 — Object State

One of the biggest differences between normal Python objects and ORM objects is that **ORM objects have a lifecycle**.

Think about a passport application.

```text
Blank Form
      │
      ▼
Filled Form
      │
      ▼
Submitted
      │
      ▼
Approved
      │
      ▼
Passport Issued
```

Similarly, an ORM object moves through different states.

```text
Python Object Created
        │
        ▼
Tracked by ORM
        │
        ▼
Saved to Database
        │
        ▼
Modified
        │
        ▼
Updated in Database
        │
        ▼
Deleted
```

Later, when we study **Sessions**, you'll learn the official SQLAlchemy states such as *transient*, *pending*, *persistent*, *deleted*, and *detached*.

For now, just understand that an ORM object has a lifecycle.

---

# Concept 6 — Identity

Imagine a school.

Student Roll Number:

```text
101 → Rahul
102 → Priya
103 → Arjun
```

There cannot be two different students with Roll Number 101.

Similarly, in a database:

```text
Students

ID   Name

1    Rahul
2    Priya
```

Inside SQLAlchemy, each database row should correspond to **one Python object** within the same session.

Conceptually:

```text
Database Row (ID=1)

        │

        ▼

Student Object

        │

Same object reused

        ▼

Student Object
```

This avoids creating multiple conflicting objects representing the same database row.

---

# Concept 7 — Relationships (Conceptual)

Real databases rarely have only one table.

Example:

```text
Students

Courses

Teachers

Departments
```

Questions:

* Which course belongs to which student?
* Which teacher teaches which course?

The database answers these using **relationships** (usually through foreign keys).

ORM lets us think naturally.

Instead of manually joining tables every time, we can conceptually think:

```text
Student

↓

Courses

↓

Teacher
```

In SQLAlchemy, relationships are represented using Python object references.

We'll study this in depth later.

---

# Concept 8 — Metadata

Think of metadata as a **blueprint of the database**.

Imagine constructing a building.

Before construction starts, you need:

```text
Rooms

Doors

Windows

Electricity

Water Lines
```

That blueprint tells builders how everything is organized.

Similarly, SQLAlchemy keeps information about:

* Tables
* Columns
* Data types
* Constraints
* Relationships

This information is called **metadata**.

It describes the database structure—not the actual data stored in it.

---

# Concept 9 — Change Tracking

One amazing feature of an ORM is that it notices when you change an object.

Example:

Initially:

```text
Student

Name = Rahul
Age = 20
```

You change:

```text
Age = 21
```

Conceptually:

```text
Old Value → 20

↓

New Value → 21

↓

ORM notices the change

↓

Generates UPDATE SQL
```

You don't manually tell SQLAlchemy:

> "Generate an UPDATE statement."

It detects the change when appropriate.

---

# Concept 10 — Unit of Work (Conceptual)

Imagine a bank employee.

You submit:

* Address change
* Phone number change
* Email update

The employee doesn't immediately process each one separately.

Instead:

```text
Collect Changes

↓

Verify

↓

Submit Together
```

ORM follows a similar concept.

It collects pending work and then applies it to the database together when requested.

This improves consistency and efficiency.

We'll explore this deeply during the **Session** topic.

# 13. Advantages of Understanding ORM Concepts

### 1. Easier Learning

Once you understand the mapping ideas, SQLAlchemy becomes much easier.

---

### 2. Better Debugging

When something goes wrong, you can identify whether the issue is with:

* the Python object,
* the ORM mapping,
* or the database.

---

### 3. Cleaner Design

You naturally design applications around domain objects instead of scattered SQL statements.

---

### 4. Easier Maintenance

Changing your application often means updating models rather than dozens of independent queries.

---

# 14. Disadvantages / Challenges

### Thinking Shift

Developers coming from SQL often need time to think in objects.

---

### Hidden Complexity

ORM makes many things easier, but it's still important to understand what happens internally.

---

### Advanced Queries

Complex reporting or analytics may still require writing SQL directly.

---

# 15. Best Practices

Senior backend developers usually:

* Design models around real business entities.
* Keep model names meaningful (`Student`, `Order`, `Invoice`).
* Avoid putting unrelated responsibilities into model classes.
* Learn both SQL and ORM.
* Understand object lifecycles before building large applications.

---

# 16. Common Beginner Mistakes

### Mistake 1

Thinking a class **is** the table.

Correct understanding:

The class **represents** the table.

---

### Mistake 2

Thinking an object automatically exists in the database.

Wrong.

An object in memory is different from a stored database row.

---

### Mistake 3

Confusing attributes with columns.

Remember:

```text
Python Attribute

↓

Database Column
```

---

### Mistake 4

Ignoring object state.

Knowing whether an object is only in memory or already stored becomes very important later.

# 24. Quiz Answers

1. Mapping is the connection between Python objects and database structures.
2. A class represents a database table.
3. An object represents one row in that table.
4. An attribute maps to a database column.
5. Metadata describes the database schema (tables, columns, constraints, etc.).
6. Identity ensures one database row is represented by one in-memory object within a session.
7. No. An object exists only in memory until it is persisted.
8. Change tracking detects modifications to ORM-managed objects so appropriate SQL can be generated.
9. Object state tells the ORM where an object is in its lifecycle.
