

# Why API Documentation Matters?

Imagine frontend team gets this API:

```http
POST /students
```

Questions:

```text
What fields are required?
What is the request format?
What response comes back?
What status codes are possible?
```

Without documentation:

```text
Frontend Team → Ask Backend Team
Backend Team → Explain Again
```

Waste of time.

---

# Good API Documentation

Should answer:

```text
What does endpoint do?
What input is expected?
What output is returned?
Possible errors?
Examples?
Authentication required?
```

# Endpoint Descriptions

Basic API

```python
@app.get("/students")
def get_students():
    return []
```

Swagger shows almost nothing.

---

Professional Version

```python
@app.get(
    "/students",
    summary="Get all students",
    description="""
    Returns a list of all students
    available in the system.
    """
)
def get_students():
    return []
```

---

Swagger now displays:

```text
Get all students

Returns a list of all students
available in the system.
```

---

# Summary vs Description

## Summary

Short.

```python
summary="Get all students"
```

Swagger:

```text
Get all students
```

---

## Description

Detailed.

```python
description="""
Returns all active students.

Supports filtering and pagination.
"""
```

---

```python
@app.get(
```


# Request Examples

Schema:

```python
from pydantic import BaseModel

class StudentCreate(
    BaseModel
):
    name: str
    age: int
```

Swagger generates generic example.

---

Better:

```python
from pydantic import Field

class StudentCreate(
    BaseModel
):

    name: str = Field(
        examples=["Ravi Kumar"]
    )

    age: int = Field(
        examples=[21]
    )
```

---

Swagger Example

```json
{
  "name":"Ravi Kumar",
  "age":21
}
```

Much clearer.

---

# Complete Example

```python
class StudentCreate(
    BaseModel
):

    name: str = Field(
        min_length=3,
        examples=["Ravi Kumar"]
    )

    age: int = Field(
        ge=18,
        le=60,
        examples=[21]
    )
```

---

# Response Examples

```python
from fastapi import status
```

# Tags & Grouping

Without tags:

```text
Swagger
--------
GET /students
POST /students
GET /courses
POST /courses
GET /users
POST /users
```

Messy.

---

Use tags.

```python
@app.get(
    "/students",
    tags=["Students"]
)
```

---

Swagger:

```text
Students
---------
GET /students
POST /students

Courses
---------
GET /courses
POST /courses
```

Professional look.

# Why API Versioning Exists

Imagine mobile app uses:

```http
GET /students
```

Response:

```json
{
  "name":"Ravi"
}
```

---

After 1 year:

Backend changes to:

```json
{
  "full_name":"Ravi"
}
```

Mobile app breaks.

Users angry.

---

Need versioning.

---

# API Versioning Strategy

## Version 1

```http
/api/v1/students
```

---

## Version 2

```http
/api/v2/students
```

---

Old clients:

```text
Use v1
```

New clients:

```text
Use v2
```

Everybody happy.

---

# Versioning Strategies

## URL Versioning (Most Common)

```http
/api/v1/users
/api/v2/users
```

Most companies use this.

---

## Header Versioning

```http
API-Version: 1
```

Less common.

---

## Query Versioning

```http
/users?version=2
```

Rare.

# Deprecation Patterns

Suppose:

```http
/api/v1/students
```

is old.

Mark as deprecated.

```python
@app.get(
    "/api/v1/students",
    deprecated=True
)
def students():
    pass
```

Swagger shows:

```text
Deprecated
```

Warning to developers.

---

# Deprecation Lifecycle

```text
v1 Released
      ↓
v2 Released
      ↓
v1 Deprecated
      ↓
Clients Migrate
      ↓
v1 Removed
```

Industry standard.
